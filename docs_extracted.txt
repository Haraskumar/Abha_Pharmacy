PRODUCT REQUIREMENTS DOCUMENT (PRD)
Abha Pharmacy Web Application — Customer Portal + Pharmacist/Admin Portal
Abha Pharmacy Digital Transformation Project | Group 20 | Version 1.1 | 13 September 2026
Document purpose
Defines the product scope, user journeys, functional requirements, business rules, acceptance criteria, and requirement traceability for the semester web application. It is the product baseline for implementation and final lab/demo verification.
Technology alignment
The submitted proposal originally names HTML/CSS/JavaScript + Python/Flask. The latest lab guidance supplied with this request changes the implementation direction to Spring Boot, with server-side rendering expected and JDBC preferred over JPA. This PRD intentionally remains technology-neutral except where that change affects product behavior.
1. Product Overview
Abha Pharmacy is a local retail pharmacy that currently depends heavily on manual records. The proposed system is a dual-sided web application: a pharmacist/admin portal for inventory, sales, alerts and fulfillment, and a customer portal for medicine discovery, prescription submission, order/refill requests and delivery/pickup workflows.
The source proposal describes a business serving roughly 150–200 transactions per day and more than 2,500 distinct SKUs. The product therefore needs a simple, reliable workflow rather than a feature-heavy marketplace experience.

Traceable transactions

Lab completeness
Every functional requirement submitted in the project proposal is demonstrably implemented and testable during the final lab/demo.

Multi-branch pharmacy operations and warehouse-level distribution.
5. Functional Requirements
ID
Requirement
Behavior
Acceptance criterion
FR-01
Dual authentication
System shall provide separate login paths/authorization for customers and staff, with role-based access control.
Login succeeds only with valid credentials; customer cannot access staff pages; unauthenticated users are redirected to login.
FR-02
Customer registration and profile
Customer shall be able to create an account and maintain CUSTOMER data: FirstName, LastName, HouseNo, Street, City, Pincode, Email, DateOfBirth and Gender; phone numbers are stored through CUSTOMER_PHONE.

Catalog search
Customer shall search medicines by medicine name and view customer-visible availability and price.
Search returns matching medicines and reflects current batch stock state.
FR-04
Medicine management
Staff shall add/update MEDICINE master data: MedicineName, GenericName, Manufacturer, Category, RequiresPrescription, ReorderThreshold, BaseUnitPrice, StorageCondition and Description.
Saved medicine persists all required master attributes and supports customer/staff search where appropriate.

Batch management
Staff shall manage BATCH data: MedicineID, BatchNo, MfgDate, ExpiryDate, QuantityInStock, CostPrice, SellingPrice, RackLocation, SupplierID, SupplyDate and PurchaseAmount.
Each batch is linked to a medicine and supplier, supports expiry/stock tracking, and retains procurement and pricing data.
FR-06
Low-stock alerts
System shall create/display an alert when stock falls below the applicable reorder threshold; the proposal explicitly cites a 10-unit example.
Alert identifies the medicine/batch context and remains visible until resolved/handled.
FR-07
Expiry alerts
System shall identify medicines/batches approaching expiry; the proposal specifies a 30-day warning window.
Dashboard visibly flags qualifying batches and supports resolution/action recording.
FR-08
POS checkout
Staff shall create walk-in sales containing one or more order items, payment method/status and discount information.
Successful checkout records ORDER and ORDER_ITEM rows and deducts sold quantity atomically.
FR-09
Digital receipt
System shall provide a receipt/confirmation view for completed sales.
Receipt shows order identifier, date/time, item quantities, sale prices and order total/discount where applicable.
FR-10
Prescription upload
Registered customer shall upload a prescription image in JPG/PNG format with pickup/delivery instructions.
Upload is associated with the customer and stored as a PRESCRIPTION record with file reference and timestamp.
FR-11
Prescription verification
Staff shall view incoming prescriptions, verify or reject them, record remarks and verification metadata.
Status transition is persisted and the responsible staff member is captured.
FR-12
Order fulfillment
Staff shall view, update and fulfill online orders, including pickup-ready notification/state.
Order status changes are auditable and customer can see current status.
FR-13
Delivery request
Customer shall be able to request home delivery for eligible refill/order workflows and provide delivery address.
Delivery order persists address fields and order type.
FR-14
Refill request
Registered customer shall be able to request a refill using prior purchase/order history.
System creates a new request linked to the customer and relevant prescription/order context where applicable.
FR-15
Order history
Customer shall view previous orders/refill requests and their statuses.
Only the authenticated customer can access their own history.
FR-16
Reports
Staff shall view daily, weekly and monthly revenue summaries from recorded orders/sales.
Totals are calculated from persisted transaction data and update when new completed sales are recorded.
FR-17
Alert resolution
Staff shall resolve alerts and record action taken, resolution status/date/time.
Resolved alert remains historically traceable rather than being silently deleted.
FR-18
Data validation
System shall validate required fields, dates, quantities, numeric ranges, file type and authorization before persistence.
Invalid input produces actionable feedback without partially committing the transaction.
FR-19
Supplier management
Staff shall maintain supplier records needed for procurement and batch receiving, including SupplierName, ContactPerson, Email, GSTIN, address and phone number(s).
Supplier data can be created/updated and selected when recording a batch; supplier identity remains traceable from batch records.
6. Core User Journeys
Customer opens catalog → searches medicine → system reads current inventory → displays available/unavailable state and customer-visible price.
Customer uploads prescription → authenticates → selects JPG/PNG → adds instructions → submits → staff sees pending verification → staff verifies/rejects with remarks.
Staff performs walk-in sale → selects item/batch and quantity → validates stock → records payment/discount → commits order and stock deduction → displays receipt.
Customer requests delivery/refill → chooses prior medication/order where applicable → supplies address/instructions → submits → staff reviews and updates fulfillment status.
System detects operational exception → creates low-stock/expiry alert → staff views alert → takes action → resolves alert with action taken/date.
7. Business Rules
Rule
Definition
BR-01
Only authenticated staff can create/update inventory, process POS sales, verify prescriptions, resolve alerts or change fulfillment status.
BR-02
A medicine may have multiple batches; stock must be maintained at batch level because expiry and sale price can differ by batch.
BR-03
A sale must not reduce stock below zero.
BR-04
Prescription-required medicines should not be treated as freely purchasable through the OTC customer flow; a verified prescription/order workflow is required.
BR-05
Low-stock threshold is stored per MEDICINE via ReorderThreshold; the project proposal uses 10 units as the example business threshold.
BR-06
Near-expiry warning window is 30 days, based on the proposal. This should be configurable in code/configuration rather than hard-coded into page text.
BR-07
Financial/transactional records are not physically deleted during normal operation; status-based closure/resolution is preferred for traceability.
BR-08
Order status, payment status and verification status should use controlled values rather than unrestricted text.
BR-09
A prescription upload must be associated with an authenticated customer and must not be publicly addressable without authorization.
BR-10
When a sale affects inventory, order creation and stock deduction must succeed together or fail together.
BR-11
Customer-facing catalog must not expose sensitive staff/internal fields such as cost price, supplier credentials or password hashes.
BR-12
The ERD/relational schema is the data-model baseline: CUSTOMER, CUSTOMER_PHONE, STAFF, STAFF_PHONE, SUPPLIER, SUPPLIER_PHONE, MEDICINE, BATCH, PRESCRIPTION, ORDER, ORDER_ITEM and ALERT.

9.2 ERD vs Relational Schema Reconciliation
The submitted ERD and relational schema are mostly aligned, but a few attributes are represented differently. The PRD follows the relational schema for implementation while documenting these differences so they are not mistaken for omissions.
Source difference
ERD submission
Relational schema submission
PRD decision
Customer phone
PhoneNumber appears inside CUSTOMER.
Phone is normalized into CUSTOMER_PHONE(CustomerID, PhoneNumber).
Use CUSTOMER_PHONE as the implementation baseline; PRD still requires customer phone capture.
Customer age
Age appears in the ERD.
No Age column in CUSTOMER.
Do not add Age as a stored field. If needed for UI, derive it from DateOfBirth; do not duplicate stored data without instructor approval.

PhoneNumber appears inside STAFF.
Phone is normalized into STAFF_PHONE(StaffID, PhoneNumber).

PhoneNumber appears inside SUPPLIER.

Use SUPPLIER_PHONE as the implementation baseline.
Order total
TotalAmount appears in ERD ORDER.
No TotalAmount column in submitted relational ORDER schema.
Treat order total as a derived value from ORDER_ITEM quantities/prices minus DiscountAmount unless the instructor explicitly requires a stored TotalAmount column.
Order-item subtotal
ItemSubtotal appears in ERD ORDER_ITEM.
No ItemSubtotal column in submitted relational ORDER_ITEM schema.
Treat subtotal as a derived value from Quantity × UnitPriceAtSale unless the instructor explicitly requires a stored ItemSubtotal column.
9.3 What This Means for the Existing Functional Requirements
No functional requirement is removed because of this review. The change is that each requirement now has explicit data coverage. In particular, medicine and batch management must expose or persist the full business-relevant attribute set, while security keys, foreign keys, audit timestamps and derived totals remain specified as system-managed data rather than being forced into customer-facing forms.
9.4 Attribute Coverage Standard
Coverage class
Meaning in this PRD
Included
The attribute is explicitly part of a business workflow, form, screen, validation rule, receipt, report, or operational record.
System-managed
The attribute is required and persisted, but generated from system events such as registration, upload, verification or resolution timestamps.
Backend relationship
The attribute connects records and is required for integrity, but is normally not a direct user-entered field.
Backend-only / restricted
The attribute is necessary for security, financial control, or access restriction and is intentionally hidden from ordinary users.
Derived
The value is calculated from persisted data and should not be duplicated as a stored column unless the instructor requires it.

Implement the complete submitted functional scope with the existing relational schema as the database contract.
Keep the architecture simple enough for lab evaluation and easy to explain in viva.

6. Critical SQL Patterns
Operation
Pattern / rule
Catalog availability
Join MEDICINE to BATCH and aggregate non-expired quantity. Do not expose cost price or internal supplier data.
Sale deduction
UPDATE BATCH SET QuantityInStock = QuantityInStock - ? WHERE MedicineID=? AND BatchNo=? AND QuantityInStock >= ?; verify updated row count equals 1.

Compare stock against MEDICINE.ReorderThreshold; create an ALERT only when an actionable condition is reached.
Expiry detection
Select batches whose ExpiryDate is within the configured warning window and whose stock is still positive.
Revenue report
Aggregate completed/qualifying ORDER rows by date range; use ORDER_ITEM for line-level totals where needed.
Order history
Filter by authenticated CustomerID. Never trust a customer-supplied CustomerID from a form.
7. Inventory and Batch Strategy
Medicine is the product/master record; Batch is the stock/expiry/pricing record.
A medicine may have multiple active batches. Stock availability shown to customers should be the sum of saleable, non-expired quantities.
For sale selection, the implementation should prefer the earliest-expiring valid batch (FEFO) when operationally practical. This is an engineering recommendation; the source documents do not explicitly mandate FEFO.
Do not sell expired batches.
Never allow a quantity update to produce negative stock.
ReorderThreshold is medicine-level in the submitted relational schema, so low-stock evaluation should compare total saleable stock for the medicine against that threshold unless the instructor asks for batch-level behavior.
